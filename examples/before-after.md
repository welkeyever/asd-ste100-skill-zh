# 中文 Before / After 示例

本文件给出 **ASD-STE100 原规则在中文语境下的对照**（第一部分）与 **本 skill 实际使用场景的对照**（第二部分：工具描述 / 错误信息 / Agent 间指令 / README 四类）。

字数统计口径：第二部分每句的字数为**中文字符数**，含标点但不含空格；1 个汉字算 1 字，1 个 ASCII 字符算 1 字。

## 第一部分 — 原规则在中文的对照

| 原规则 | Before | After | 为什么 |
|---|---|---|---|
| 术语一致（一词一义） | "**检查**系统 / **验证**连接 / **确认**接收。" | "**检查**系统 / **检查**连接 / **检查**接收。" | 三个近义词让读者猜它们是不是指同一个动作。挑一个用到底。 |
| 词性一致 | "给资源**锁**三秒。" | "给资源**加锁**三秒。" | 名词"锁"被当动词用，和下文"把**锁**移到独占模式"冲突。统一动词形式。 |
| 精准动词义 | "**遵循**安全须知。" | "**执行**安全须知。" | "遵循"既可表示"随后"也可表示"服从"。挑没有歧义的那个。 |
| 体标记一致（替换"简单时态"） | "任务**正在**启动**中**。" | "任务**正在**启动。" | "正在" 和 "中" 语义重复。保留一个。 |
| 动词形式优先（Rule 3.7） | "**对**筛选器**进行检查**。" | "**检查**筛选器。" | 虚化动词 "进行" 加名词 "检查" 把动词藏起来，还多了一个没信息的填充词。 |
| 禁虚化动词 + 名词化 | "**完成**服务**的部署**。" | "**部署**服务。" | 对应原规范"no phrasal verbs"的中文版——"完成 / 做出 / 实施 / 开展 / 发出 + 名词"是中文最常见的赘述。 |

## 第二部分 — 实际场景

### 例 A — 工具描述

**Before:**

> 本工具会尝试在已经被配置的各个后端之间进行状态的同步，如果检测到冲突可能会根据已经设定好的策略来自动进行解决，否则会把冲突暴露出来以供人工审查。

**违反的规则：**

- **流水句**：一句话讲三件事（同步 / 自动解决 / 暴露冲突），用逗号串联。
- **虚化动词 + 名词化**：
  - "进行状态的同步" → "同步状态"
  - "进行解决" → "解决"
- **"的"字堆叠**：
  - "**已经被配置的**各个后端"
  - "**已经设定好的**策略"
- **被动语态**：
  - "被配置的" "被设定" "暴露出来" "以供人工审查"——施事者不明确
- **句长**：75 字，远超描述句 ≤ 50 字的硬上限

**没有被标记（刻意保留）：** "会尝试" 和 "可能会" 都是情态词，表达"工具不保证成功"。改写不能把它们改成"工具会同步"或"工具解决冲突"——那是改断言，不是改写。

**After:**

> 本工具尝试同步已配置后端之间的状态。如果检测到冲突，工具按预设策略处理：允许自动解决时，工具可能自动解决冲突；不允许时，工具把冲突报告给人工审查。

字数：第一句 15 字，第二句 46 字。全部主动语态，情态词"尝试 / 可能"保留。

### 例 B — 错误信息

**Before:**

> 由于预期的数据格式可能存在不匹配的问题，在处理您的请求的过程中可能发生了错误，这有可能是由于客户端版本过旧所引起的。

**违反的规则：**

- **流水句**：一句话三件事（发生错误 / 格式不匹配 / 客户端过旧）。
- **"的"字堆叠**："**预期的**数据格式" / "**不匹配的**问题" / "**您的**请求" / "**处理您的请求的**过程"（最后一个连续 3 个"的"）。
- **情态堆叠**："**可能**存在不匹配的问题" + "**可能**发生了错误" + "**有可能**是..." + "**所引起的**"——四层。
- **被动语态**："所引起的" 没有明确施事者；中文更应该写成主动句。
- **句长**：53 字。

**没有被标记（刻意保留）：** 两个"可能"必须保留——系统写这条错误时并不知道实际发生了什么，情态词如实表达了这种不确定。

**After:**

> 处理请求时可能发生了错误。原因可能是数据格式不符合服务端预期。过旧的客户端版本可能导致这种不匹配。请检查客户端版本。

四句，分别 14 字、21 字、20 字、11 字。情态词"可能 / 可能导致"保留，错误原因拆成三个独立断言，最后给出可执行动作。

> **这个例子是情态规则存在的理由。** 本文件早期一版把第一句写成"处理请求时发生了错误"——读起来更干净。错——系统并不知道有没有真的失败。一句读起来更好的改写如果**升级**了情态强度，就不再是改写，而是另一个断言。

### 例 C — Agent 间指令

**Before:**

> 当上游任务已经完成了并且假设没有抛出错误的话，下游 agent 应该继续去消费输出的制品，但是值得注意的是，在超时的情况下有时候会产出部分制品。

**违反的规则：**

- **"已经 ... 了"** 体标记重复。
- **流水句**：一句话四件事（上游完成 / 无错误 / 下游继续 / 超时警告）。
- **情态堆叠**："假设 ... 的话" "应该继续去" "值得注意的是" "有时候会"——四层。
- **零宾语歧义**："消费输出的制品" ——消费什么样的输出的制品？"输出的"修饰"制品"，可以但不清晰。
- **互联网黑话** / **营销词**：无（这段比较朴素）。
- **句长**：67 字，超指令句 40 字上限。

**After:**

> 等上游任务完成且无错误。然后下游 agent 读取输出制品。警告：超时会产出不完整的制品。使用前检查制品完整性。

两处值得单独说明：

- "**应该继续去消费**" 改成祈使 "**读取**"。原 ASD-STE100 允许这个转化——面向执行者的建议在指令类文本里就是命令。描述类文本里**不要**这样换。
- **最后一句是新增内容**。原文只警告了"会产出部分制品"但没说该怎么办。本 skill 的边界是"不加原文没说的事实"，但"检查制品完整性"是**警告的隐含动作**，严格说处于边界上。如果原作者的沉默是刻意的（例如下游 agent 不应该做这个检查），就应该删掉这一句。**这类加法必须显式标注**，让用户决定留还是去。

### 例 D — README 段落（偏意模式）

**Before:**

> 我们的缓存层通过业界领先的语义相似度算法，无缝接入您现有的技术栈，极致提升开发体验；它赋能开发者打通上下游链路，一站式降低 LLM 场景下传统缓存经常面临的高未命中率问题，助力业务快速落地。

**违反的规则：**

- **互联网黑话 / 营销词**：业界领先、无缝、极致、赋能、打通、链路、一站式、助力、落地——9 个。
- **流水句**：分号把两个独立断言连起来。
- **禁分号**。
- **名词化**："降低 ... 高未命中率问题" ——用动词更干脆。
- **句长**：84 字。

**After:**

> 普通缓存按文本精确匹配，输入稍变就 miss。本缓存比较新 prompt 和已有 prompt 的语义，而不是文本。它与现有技术栈并行运行，不额外存储数据。

偏意模式保留了解释的节奏——没有强推严格的"术语一致"（"miss"的中文对应多个说法，偏意模式允许保留 miss 这个开发者圈子通用的英文词），但删掉了所有营销词、分号、流水句，并把 84 字拆到 20 字 + 29 字 + 23 字。

## 怎么读这些例子

第一部分演示本 skill 实际检查的规则，第二部分演示它们怎么在真实 agent 场景下迁移。核心能力是一样的——**一句一指令、短句、主动语态、保留情态、术语一致**——这些让 agent-to-agent 和跨语言文本更安全地被解析，而不只是飞机维修手册。

有一类错误特别容易在中文里犯：**为了短句而删掉情态词**。例 B 和例 D 都触及这个坑。看到"可能 / 也许 / 或许"时，先问自己："删了之后，这句话还是原来那个断言吗？"——不是，就留着。
