# 中文规则的设计依据

本项目借鉴 ASD-STE100 的清晰表达原则，为中文技术文本设计独立的改写策略。它不是官方中文版、完整规则翻译或合规认证工具。实际执行约束以 [SKILL.md](../SKILL.md) 为准。

## 来源与本地约定

ASD 官方介绍列出了 Issue 9（2025 年 1 月）的 53 条写作规则和受控词典。原标准面向英语；本仓库不复制其词典，也不把中文策略标成原标准的逐条对应实现。版本和内容应以[官方介绍](https://www.asd-ste100.org/about_STE.html)及[官方下载入口](https://www.asd-ste100.org/STE_downloads.html)为准。

早期版本把中文规则直接挂到未经核实的英文规则编号，并用“1 个英文词约等于 2 个汉字”推导句长。现在去掉这类对应关系：**40 / 50 字是本项目可调整的表达预算，没有等价换算或效果实验的依据。**

## 保留哪些原则

| 原则 | 中文适配 | 使用边界 |
|---|---|---|
| 用常见、明确的词 | 优先读者熟悉的动作词和项目术语 | 专业词比通俗替代词更准确时保留专业词 |
| 同一含义使用稳定术语 | 确认指向同一对象后再统一名称 | 不能把客户与操作员、验证与审核等不同概念合并 |
| 让操作易于执行 | 分开独立步骤，显式绑定条件与动作 | 拆句不应把条件动作变成无条件动作，也不应强加顺序 |
| 适当使用主动表达 | 主体已知且关系不清时补明主体 | 状态报告可以用“文件已删除”；主体未知时不猜测 |
| 缩短句子和定语 | 先消除不必要的嵌套，再考虑拆句 | 数字、单位、例外、限定和情态的优先级高于字数 |

## 中文中的重点判断

### 虚化动词与动作阶段

“对日志进行分析”通常可以简化为“分析日志”。但“完成部署”包含完成要求，“发出通知”可能区别于“收到通知”。不能把“完成 / 发出 + 名词”一律视为赘述。linter 保留候选提示，不自动替换。

### 情态、体标记与否定

“可能已经失败”同时表达不确定性和时间状态，两者都要保留。“已经完成了部署”是自然的中文表达，不自动判错。“正在启动中”可以考虑简化，但要确认“中”确实是状态标记，而不是“中间服务”这类对象的一部分。

情态保真不能靠统计“可能”出现几次来证明。“可能不失败”与“不可能失败”包含相同词语，含义不同。应检查否定和情态的作用域。

### 省略与歧义

“打开文件。读取第 3 行。”在操作者和文件明确时无需补主语。“完成后检查”缺少任务、操作者和检查对象，不能凭空改成“任务完成后，用户检查输出文件”。可先处理其余明确部分，再指出缺口。

“否则”可能指条件不成立，也可能指处理失败。没有上下文时不能把它改成某个具体失败分支。

### 术语、代码与中英混排

允许“请求（request）”这样的术语介绍。描述中的“请求”和字段 `request` 可以并存。字段名、代码、命令、URL、路径和占位符保持原样。术语一致性基于指向与含义，而不是词形是否相似。

### 黑话、四字词与营销描述

“对齐”可能是模糊的协作表达，也可能指字节对齐。“链路”可能是网络术语。“原子操作”有四个字，却不是修辞。词表只用于提出候选，不足以决定删除。

营销描述缺少依据时，指出缺口。不要为了把“极致提升性能”写具体而添加吞吐量、缓存机制或部署承诺。删除修饰后仍要保留原文表达的功能与目标。

## 自动检查与语义审查的分工

linter 可定位标点、字符预算和部分表面模式。它不能判断改写是否保持含义，也没有中文分词或句法分析器。硬检查是项目可配置的格式约定；建议项必须结合上下文判断。详见 [linter 说明](linter.md)。

改写效果通过成对案例审查，方法见 [效果评估](../evals/README.md)。目前没有发布“降低 Agent 错误率”的实验结论。
