# 改写效果评估

核心问题是：**保持含义的同时，读者是否更容易理解和执行？** linter 测试只验证脚本行为，不能回答这个问题。

[cases.json](cases.json) 包含 20 个人工构造的输入和逐项判据，覆盖情态、完成状态、条件、否定、权限、数字、术语、接口、并行关系、歧义处理和无需改写的文本。它是回归用例集，不代表真实场景的统计分布，也没有模型运行成绩。

## 怎样比较版本

1. 固定模型及其完整版本、运行日期、采样配置和系统提示。记录仓库提交或工作区快照标识。
2. 每个案例分别在独立会话运行基线和候选版本。初次比较可用“普通重写提示”作为基线；后续比较用上一版 skill。除 skill 指引外保持输入相同。
3. 给模型的输入只包含 `mode` 和 `source`；`criteria`、`protected` 只供事后评审，不作为模型提示。避免把期望答案提前交给模型。
4. 每个案例、每个版本至少运行 3 次，保存未经人工修改的输出和澄清问题。若模型提出问题，记录为待澄清，不擅自补答案继续。
5. 隐去版本标签，逐条核对 `criteria`。如有第二位评审者，请独立判断，再处理分歧。

重写任务提示模板：

```text
按简化中文技术写作规则处理以下文本，使用指定模式。
默认只返回改后文本。关键歧义无法消除时保留并指出缺口，或提出澄清问题。

模式：<mode>
原文：
<source>
```

基线无 skill 时保留同样的任务提示。比较 skill 版本时，分别加载对应的完整 `SKILL.md` 及按需引用的资源。

## 怎样判定

先判语义，再判清晰度：

| 维度 | 记录方式 |
|---|---|
| 语义保真 | 所有判据满足才算通过。任一事实、情态、条件、否定、主体、数字或顺序改变，都记失败并引用证据 |
| 接口保留 | 核对 `protected` 中每个字符串是否原样保留。字符串相同仍不保证其使用含义相同 |
| 歧义处理 | 含糊案例应保留缺口或澄清；把猜测写成事实记失败 |
| 清晰度 | 仅对语义通过的输出评为改善 / 持平 / 退化，并指出具体原因 |
| 最小改动 | 清楚的原文可以原样返回，不把修改数量当成收益 |
| 格式遵循 | 检查默认正文、解释表或审查输出是否符合用户请求 |

报告语义失败数 / 总运行数、清晰度分布、各类失败示例和待澄清数。澄清不自动算失败：`ambiguous-else` 和 `unknown-actor` 本来就缺少信息。应按其判据评审，不能把“改写成功率”定义为一定给出完整改写。

## 记录格式

可把每次运行写成一条 JSONL：

```json
{"case_id":"completion-state","variant":"candidate","repeat":1,"model":"实际模型版本","skill_revision":"实际提交或快照","output":"实际原始输出","semantic_pass":true,"clarity":"unchanged","notes":"已核对完成状态"}
```

这里是格式示例，`semantic_pass` 必须在评审实际输出后填写。发布成绩时附提示、模型、版本、采样设置、原始输出和评审方法，不只公布一个百分比。

## 使用边界

测试集可以帮助发现回归，不能证明未知文本一定安全。需要评估“下游 Agent 是否少出错”时，应另外设计真实任务：让下游分别读取原文与改写，记录实际动作和正确率。当前仓库没有这类实验证据。
